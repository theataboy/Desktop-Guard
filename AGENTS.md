# Repository guidance

## Product requirements

- Desktop Guard v1 targets Windows 11 and uses .NET 10 with Windows Forms.
- All user-facing application text is English in v1. Keep UI strings in `src/DesktopGuard.App/Resources/Strings.resx` and access them through the app's resource wrapper. English is the neutral fallback; add culture-specific resource files only when another language is requested. Do not add a language picker before then.
- Keep `SatelliteResourceLanguages` limited to `en-US` for v1; expand it when another UI language is added.
- Use `NotifyIcon` for the tray icon/menu and Windows App SDK `AppNotificationManager` for Windows notifications. Keep this integration in `DesktopGuard.App`; bundle the Windows App SDK runtime for the unpackaged local-folder release.
- Preserve the v1 behavior documented in `README.portable.md`: monitor and manage `.lnk` and `.url` files on both the user and Public desktops. Existing Public links form the approved baseline; new Public links are pending review and remain untouched until the user acts. Discovery and approval never elevate. Observe other file types without modifying them.
- Treat the first complete scan of each desktop as its baseline. Do not classify existing items as new. If the user Desktop path changes, preserve its prior decisions and require review instead of silently establishing a new baseline.
- Never delete desktop files automatically. Parking and restore operations must be reversible, preserve the original Desktop location, and avoid overwriting an existing file; restore may use a numbered basename when the original name is occupied.
- Provide explicit shortcut actions to rename only the basename while preserving `.lnk` or `.url`, open the Windows Properties window, and delete. Desktop deletion goes to the signed-in user's Windows Recycle Bin without a separate DG confirmation; manual deletion from Recovery is permanent and requires confirmation. Automatically remove verified Recovery duplicates with the same launch fingerprint, Desktop root, and DG-created marker, keeping the newest last-write time (first stored record on a tie). Re-read both files and verify their byte hashes while locking the survivor before deleting the duplicate. Never elevate this cleanup; report failures and show one summary notification after cleanup.
- Keep hidden shortcuts in the normal list and filters and label them **Hidden**. Offer an explicit Make visible action for hidden shortcuts on a Desktop or in Recovery. Preserve Hidden while parking into Recovery, but clear it whenever DG publishes a shortcut to a Desktop, including restore and moves between desktops. DG-created Desktop shortcuts must not be hidden.
- Keep rename, Properties, Make visible, and Delete together in one selected-shortcut **More shortcut actions** menu so they do not crowd the primary action bar. Do not add a separate Hidden filter in v1.
- Support **Ctrl+F** to focus search and **F2** and **Delete** for the selected shortcut when the list has focus and the action is available. Keyboard actions must use the same selection checks, file-operation validation, and delete behavior as the corresponding UI actions.
- Settings provides **Apply** to save without closing, **Save** to save and close, and **Cancel** to discard changes. Closing with unsaved changes prompts to save, discard, or return. **Enter** and **Ctrl+S** save; **Escape** cancels; buttons have standard Alt access keys.
- Park after an explicit user action, or automatically re-park a shortcut whose saved launch-identity fingerprint matches a still-parked shortcut on the same Desktop. Automatic re-parking waits the user-configured 2–30 minute delay (default 5), then requires the same stable-file checks and final source recheck. Never elevate automatically. A stable-file check is a race guard, not proof that an installer has finished.
- For launch-identity matching, read at most 1 MiB from a validated `.lnk` or 64 KiB from a `.url` file during a complete scan, explicit parking, validated Recovery backfill, or fresh Recovery duplicate check. Limit each parsed launch-metadata or URL field to 8,192 characters. Store only a versioned SHA-256 fingerprint of target/arguments/working-directory data (or the URL value); never execute or resolve targets. Unreadable or oversized shortcuts remain eligible for ordinary review.
- Store user state and recovery data under `%LOCALAPPDATA%\DesktopGuard`, never in the repository or beside the executable.
- Keep the event log local and limited to the file name, path, and timestamp; prune entries older than 90 days. Provide recovery-folder commands in both the tray menu and main window.
- Start at sign-in is enabled by default and can be disabled. Starting minimized is also enabled by default and can be changed in Settings. Keep the main window hidden until this preference has loaded. Register only DG's own value under the current user's `Run` key; include only DG's fixed `--background` argument when that preference is enabled; never use a service.
- Distribute DG as a portable ZIP, not an installer. Recommend a stable program folder under the signed-in user's profile with normal per-user ACLs; avoid shared or Public folders. On each launch, the existing startup manager updates DG's own `Run` value to the absolute path of the running executable. Do not add a service, updater, or machine-wide registration for portable deployment.
- Mark the Desktop launcher created by DG in persisted shortcut state. It is a per-user launcher and must not be moved to Public Desktop, including after rename. Do not infer this marker for completed shortcuts in old state based only on their name; mark only a validated in-progress `Creating` operation during migration.
- Treat file-system watcher events as coalesced hints. Keep the queue bounded and perform a full scan at startup, after watcher errors, and periodically.
- Show at most five Windows notifications per scan. Keep the review list authoritative if Windows suppresses notifications; notification arguments may contain only validated opaque shortcut IDs.

## Security requirements

- Treat security as a requirement for every design, implementation, review, and release change. Read `SECURITY.md` before feature work and update its threat model when a change adds an input, dependency, permission, or file operation.
- Treat filenames, paths, shortcut contents, filesystem events, saved state, and notification activation data as untrusted. Never execute, launch, or resolve a shortcut target. The bounded launch-identity reads below are the only exception for parsing raw launch metadata.
- Treat file attributes, including Hidden, as untrusted inventory data. Observe attribute changes; changing visibility must alter only the Hidden bit. Open the Windows Properties verb only for an explicitly selected validated `.lnk` or `.url` file.
- Validate leaf names using Windows filename rules. Reject alternate data stream syntax, reserved device names, invalid characters, and trailing spaces or dots before tracking or operating on a shortcut.
- Resolve Desktop roots through Windows known-folder APIs. Inspect only direct children; validate canonical candidate paths remain under the selected root and reject candidate reparse points. Recheck the source immediately before a file operation.
- Persist operation intent before parking, restoring, moving between desktops, renaming, or deleting. Create move destinations under a hidden operation-specific staging directory within the destination folder so the file inherits destination ACLs. Verify copied bytes before removing the source. Rename without overwriting and update a Desktop checkpoint only when the renamed shortcut is currently on a Desktop. Reconcile interrupted actions automatically only when exactly one safe endpoint exists; allow a user-requested retry to clean only that operation's validated staging directory.
- A Public path change preserves previous decisions and blocks operations on the changed root. For schema v1 migration, preserve the existing Public checkpoint as the approved baseline; entries absent from that checkpoint become pending after upgrade.
- Schema v6 introduced the persisted DG-created marker. Preserve its migration rules when upgrading: mark only a validated in-progress `Creating` shortcut and leave completed shortcuts unmarked. Existing DG launchers from older versions must be explicitly removed and recreated by the user.
- Schema v7 adds the 5-minute default auto-parking delay and optional shortcut-identity hashes. Migrate older states without changing decisions or checkpoints, and safely backfill identities from validated parked Recovery files when possible. Keep unparseable items intact and let their re-created copies go to review.
- Schema v8 adds a persisted flag for the one-time comparison of existing pending shortcuts and a distinct Recovery duplicate-removal operation. Preserve v7 fingerprints and decisions during migration. Compare existing pending shortcuts once with parked rules using the normal delay; preserve approved decisions. Reconcile interrupted duplicate removal by file presence, and require a fresh duplicate check before any later automatic deletion.
- Schema v9 uses the persisted target-name field for restore and desktop-move destinations. Migrate v8 without changing decisions, checkpoints, or names; an older interrupted operation with no target name continues using its original basename. On a name conflict, choose the lowest free `(2)`, `(3)`, and later suffix in the exact destination folder, preserving the extension. The same basename in the other Desktop folder is allowed. Keep the Desktop Guard launcher duplicate checks fail-closed.
- Keep the main app asInvoker and do not use a Windows service. Discovery and state-only approval never elevate. After an explicit file operation fails with Win32 Access Denied, a one-operation helper may relaunch the same executable with `runas`; sharing and lock errors never trigger UAC. The helper accepts only a fixed operation, opaque IDs, root kinds, validated shortcut names, and validated target basenames for rename, restore, and desktop moves; it derives the original interactive user's known folders and never accepts arbitrary paths or commands. Recycle Bin deletion in the helper must fail closed if the elevated SID differs from the interactive user's SID. Do not add network access, telemetry, or secret storage to the DG v1 runtime.
- Fail closed on ambiguous paths, malformed state, access errors, and collisions: preserve the original and recovery data, show a clear error, and never overwrite or automatically delete a desktop file. Explicit deletion is limited to the selected shortcut and follows the destination-specific Recycle Bin or confirmed permanent-delete behavior above.
- Bound filesystem-event queues and notification text. Notification activation must use validated opaque identifiers, never raw paths.
- Do not suppress a security analyzer or dependency-audit finding without recording its reason and mitigation in `SECURITY.md`.

## Architecture and code

- Keep policy and state transitions in `DesktopGuard.Core`; keep WinForms, shell, startup, notifications, and filesystem integration in `DesktopGuard.App`.
- Keep `DesktopGuard.Core` platform-independent: it must not reference `DesktopGuard.App`, WinForms, Windows APIs, or perform filesystem, registry, notification, or process operations directly. Put required capabilities behind narrow interfaces and implement them in `DesktopGuard.App`.
- Keep project references one-way: `DesktopGuard.App` may reference `DesktopGuard.Core`; `DesktopGuard.Tests` may reference the projects it needs for focused tests; production projects must never reference test projects. Do not add projects or architectural layers without a concrete requirement.
- Keep WinForms event handlers and presentation code thin. They translate user actions into application operations and display results; policy decisions and state transitions belong in `DesktopGuard.Core`.
- Organize code by responsibility and, when a feature grows, by feature within its owning project. Use `DesktopGuard.Core` folders for domain policy/state and `DesktopGuard.App` folders for presentation, Windows integration, and persistence. Keep `Program.cs` at the app entry point and UI resources under `Resources`.
- Create a folder only when it has files to own. Avoid generic dumping grounds such as `Helpers`, `Utils`, or an all-purpose `Services` folder; name folders and types after the product responsibility they implement.
- Before adding a type, check whether an existing type already owns that responsibility and place the new type in the correct project and feature folder. Prefer focused types with one clear reason to change; avoid both oversized classes and one-line wrapper types that add no useful boundary.
- Put each meaningful top-level type in a correspondingly named source file. Keep namespaces aligned with the project and folder structure. Partial types are reserved for framework-generated patterns such as WinForms Designer files; do not split a type across files otherwise.
- Add an interface when it defines a real boundary, such as operating-system or storage access, or enables a meaningful test seam. Do not add interfaces, dependency-injection frameworks, base classes, or design patterns mechanically for every type.
- Keep dependencies flowing inward: presentation and Windows adapters call application/policy code; core policy does not depend on its callers. Avoid duplicate implementations of the same rule; give each rule one clear owner.
- Use nullable reference types, implicit usings, file-scoped namespaces, descriptive names, and the repository `.editorconfig`.
- Keep platform-independent core policy tests in `tests/DesktopGuard.Tests` using MSTest. Put Windows filesystem/UI integration tests in a separate Windows-targeted test project only when that boundary warrants it. Filesystem tests must use temporary directories, never the real user or Public Desktop.
- Mirror the production responsibility/feature names in the test folder structure. Name tests for observable behavior and include regression coverage when fixing a defect.
- Keep dependencies minimal. Add a package only when it provides a clear need that the .NET platform does not already meet.
- Keep operations on desktop files explicit and recoverable. Report access or move failures without silently treating inaccessible locations as empty.

### Initial project map

- `src/DesktopGuard.Core`: desktop inventory policy, shortcut state transitions, reconciliation, and state validation.
- `src/DesktopGuard.App`: `Application` orchestration; `DesktopScanning` scanner and bounded monitor; `Notifications`; `Persistence`; `ShortcutManagement`; `Startup`; WinForms entry point, main window, tray context, and `Resources`.
- `tests/DesktopGuard.Tests`: platform-independent scanning policy, reconciliation, validation, and shortcut transition tests.
- `tests/DesktopGuard.App.Tests`: Windows scanning and monitoring, notification activation, persistence, and file-operation tests. File operations use temporary directories, never actual Desktop folders.
- `scripts/package-portable.ps1`: locked restore, self-contained publish, and ZIP packaging for portable release.
- `README.md`: project overview and developer commands; `README.portable.md`: end-user setup, usage, and maintenance guide, packaged as `README.md` and rendered as `README.html`; `SECURITY.md`: threat model and security requirements; `AGENTS.md`: durable coding and repository rules.

This map is an ownership guide, not a requirement to create empty folders in advance. Add feature folders when implementation gives them a clear purpose, and update this map if a deliberate architecture change alters project ownership or dependencies.

## Repository workflow

- Build from the solution root with `dotnet build DesktopGuard.sln`.
- Run core tests with `dotnet test DesktopGuard.sln` when validation is requested.
- Audit direct and transitive NuGet packages with `dotnet package list --vulnerable --include-transitive` before release.
- Use `dotnet restore --locked-mode` for release builds; update and review package lock files when dependencies change.
- Check formatting from the solution root with `dotnet format DesktopGuard.sln --verify-no-changes`.
- Publish the self-contained compressed x64 executable with `dotnet publish src/DesktopGuard.App/DesktopGuard.App.csproj -c Release -p:PublishProfile=SelfContainedSingleFile -p:DebugSymbols=false -p:DebugType=None`.
- Package the portable release with `scripts/package-portable.ps1`; its output is `artifacts/portable/DesktopGuard-win-x64.zip` and contains the executable, the guide as `README.md` and `README.html`, `DesktopGuard.ico`, and LICENSE.
- Keep generated `bin`, `obj`, test, and publish output out of Git.
- Preserve user changes. Do not stage or commit unless explicitly asked.
