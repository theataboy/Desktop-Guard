# Desktop Guard security baseline

Security is a requirement at design, implementation, review, and release. Revisit this document whenever a feature adds an input, dependency, permission, or file operation.

## Security goal and limits

DG is a least-privilege tool for detecting and explicitly managing desktop shortcuts. Parking and restore are reversible; a user may also choose to send a desktop shortcut to the Recycle Bin or permanently delete one from Recovery. DG is not an antivirus product or a security boundary. It cannot protect a user's files or DG's per-user state from a malicious process already running as that user, or from an administrator.

DG also automatically removes duplicate Recovery copies after verifying equal launch fingerprints within the same Desktop root and DG-created marker. This intentionally treats shortcuts with different descriptions, icons, or other non-identity metadata as duplicates. It permanently removes the older last-write time, keeping the first stored record if dates tie. Copy-based moves preserve the source last-write time so a later parking action does not make an older shortcut appear newer. Older Recovery files may already have transfer dates that cannot be reconstructed. Last-write time selects a preferred copy; it is untrusted metadata and does not prove installation order.

## Assets and trust boundaries

- Desktop and Public Desktop entries, including `.lnk` and `.url` contents.
- DG's local settings, inventory, event log, and recovery files.
- Filesystem watcher events and Windows notification activation data.
- The current user's startup `Run` registry value and the path to the running DG executable.
- The current user's Windows app-theme preference, used only to choose presentation colors.
- The About window's fixed Releases URL, packaged `LICENSE` and `README.html` files, and the Windows applications opened after an explicit user click.
- Keyboard and pointer actions in the main window, including commands that rename or delete a selected shortcut.
- Build dependencies and the published application folder.
- The portable ZIP and the user-selected folder from which the executable runs, including the path written to the current user's startup `Run` value.
- Release tags, GitHub Actions workflows and pinned action dependencies, temporary package artifacts, and the workflow's scoped `GITHUB_TOKEN`.

Treat all of these inputs as untrusted, including data read back from DG's own files.

## Required controls

- Keep the main process at `asInvoker`; do not add a privileged service, network access, telemetry, or secret storage. Discovery and state-only approval never elevate. Only an explicit file operation that receives Win32 `ERROR_ACCESS_DENIED` may launch the same executable once with the `runas` verb. Sharing and lock violations never trigger UAC. Treat cancellation and every nonzero helper result as a failed operation.
- About actions accept no user-supplied paths, commands, or URLs. Open the fixed Releases URL only in response to a click through the Windows shell; Desktop Guard performs no HTTP request. Open only direct-child `LICENSE` and `README.html` files beside the running executable, reject directories and reparse points, and pass the license path as a single argument to Windows Notepad.
- Keep elevated work in a command-only helper path that returns before WinForms, notifications, startup registration, or state-store initialization. Its bounded request contains a fixed operation enum, root kinds, opaque shortcut and operation IDs, recovery ID when required, and validated source and target basenames. Restore and desktop-move target basenames come from the persisted operation intent and must be validated just like rename targets. It accepts no caller-supplied path or command. Derive User Desktop and Local AppData from the interactive shell user's token, not from the elevated account; derive Public Desktop through the Windows known-folder provider. Validate that every resulting source and destination is a direct child of an allowed root before acting.
- Resolve Desktop roots through Windows known-folder APIs. Scan only direct children. Accept the OS-selected root path, including a redirected Desktop, but reject candidate entries that escape that root or are reparse points.
- During inventory discovery, read only top-level entry names and filesystem attributes. Exclude directories, including directory reparse points, without making the root incomplete. Reject direct-child file reparse points (including cloud placeholders) and keep the root incomplete until a complete scan can verify its entries.
- Classify shortcuts by the `.lnk` and `.url` extensions only. Never execute, launch, or resolve a shortcut target. For recurrence matching and Recovery duplicate verification, read at most 1 MiB from a validated regular `.lnk` or 64 KiB from a `.url` file during complete scans, explicit parking, validated Recovery backfill, or a fresh duplicate check, without following reparse points. Parse `.lnk` raw target path, arguments, and working directory without calling `IShellLink::Resolve`; limit each parsed field and the `.url` `URL` value to 8,192 characters. Parse only the `.url` `URL` value and make no network request. Do not expand environment variables or check target existence. Store only a versioned SHA-256 fingerprint, never raw launch metadata. If parsing fails or a field exceeds its bound, do not suppress review or automatic parking based on name alone.
- Validate leaf names using Windows filename rules before tracking or operating on them. Reject alternate data stream syntax, reserved device names, invalid characters, and trailing spaces or dots.
- Treat watcher events as hints. Reconcile with directory scans, validate each candidate again immediately before acting, and bound/deduplicate event queues.
- Read the Hidden attribute during direct-child inventory, include attribute changes in watcher hints, and keep hidden shortcuts in the same review and recovery filters. Label hidden entries in the list. Do not create DG shortcuts with Hidden set. Preserve Hidden when parking into Recovery, clear only Hidden whenever restoring or moving a shortcut onto either Desktop, and offer an explicit Make visible action for hidden shortcuts on a Desktop or in Recovery.
- Use a capacity-one coalesced watcher signal queue. Run full scans at startup, after watcher errors, and periodically; do not use event-provided paths as candidates.
- Replace a watcher that reported an error before relying on it for new change hints; periodic scans remain the fallback if watcher creation fails.
- Park after an explicit user action, or automatically re-park a new shortcut when its identity fingerprint matches a still-parked shortcut on the same Desktop. Use the saved 2–30 minute user setting (default 5 minutes), measured from first observation, then perform two stable checks at least one second apart and a final source recheck immediately before moving. Persist a source-byte SHA-256 for scheduled shortcuts and send a changed or unreadable file to review; legacy schedules without this hash also go to review. For automatic moves, verify the exact source-byte SHA-256 against the bytes used to derive the identity while the source is locked; on mismatch, leave the file and send it to review. Automatic parking never invokes UAC. The stability check is a race guard, not evidence that an installer finished.
- Create the DG Desktop shortcut only after an explicit user action and complete scans of the current User and Public Desktops. Refuse creation when a `Desktop Guard.lnk` is tracked on either desktop or parked in recovery, and recheck both destinations immediately before publication. Resolve the User destination from the Windows known-folder provider, validate the exact fixed leaf name and direct-child path, and recheck the User root and destination immediately before publication. Write the link under an operation-specific hidden staging directory inside that Desktop, persist its expected content hash before publishing, and use a no-overwrite move. This creation path never invokes the elevation helper.
- Before restoring a parked `Desktop Guard.lnk`, check the other current Desktop and fail closed if it already contains that link. Never create or automatically remove a second copy to resolve a duplicate; keep both files and recovery data for an explicit user decision.
- Move only between the current user's Desktop, Public Desktop, and a per-shortcut folder under DG's local Recovery directory. Persist operation intent first. For restore and desktop moves, if the requested basename is occupied in the exact destination folder, choose the lowest free `(2)`, `(3)`, and subsequent suffix before the extension; compare names case-insensitively and count every direct child entry as occupied. A same-named item in the other Desktop folder does not conflict. Persist the selected target basename and use it during retry and reconciliation. Keep the Desktop Guard launcher duplicate checks fail-closed. Create destination files under a hidden operation-specific staging directory inside the destination folder so the final shortcut inherits that folder's ACL; verify the opaque bytes before removing the source and preserve the source last-write time. Reconcile interrupted moves automatically only when exactly one safe endpoint exists. A manual retry may clean only the exact operation-owned staging directory and resume the same persisted operation. Never overwrite a desktop shortcut; if the selected target becomes occupied before publication, preserve both files and report the failure. Rename only the basename and keep its extension, use a no-overwrite rename, and update a Desktop checkpoint only for a shortcut currently on a Desktop. A shortcut explicitly deleted from a Desktop goes to the signed-in user's Recycle Bin; a shortcut explicitly deleted from Recovery is permanently removed only after the UI confirmation. Persist delete intent first and reconcile a missing source as completed. Make visible changes only the Hidden attribute. Open Windows Properties only after an explicit action for the validated `.lnk` or `.url` itself; never invoke its target. On ambiguous paths, source replacement, corrupt state, access errors, or locks, preserve files and report the failure.
- During a copy-based move, open the source and comparison files without following reparse points and validate attributes on the opened handles. Keep the source open with read and delete access while denying new writes and renames. Compare the copied destination while it is also protected from replacement, then mark the verified source handle for deletion. A sharing violation fails the move. Case-only renames require an exact on-disk leaf-name check when reconciling an interrupted operation. Complete scans update the saved casing of an idle tracked shortcut after an external case-only rename without resetting its decision.
- For automatic Recovery duplicate removal, freshly parse both validated Recovery files, require fingerprints to match their saved identities, and limit each scan to 64 candidate reads of at most 1 MiB. Persist a distinct removal intent before deleting. Lock the retained copy against writes and deletion, then open the duplicate with delete access, verify both full-file SHA-256 hashes against the freshly parsed bytes, and delete only the duplicate through its verified handle. A missing, changed, locked, inaccessible, or reparse-point file preserves the duplicate and produces a visible issue. Never invoke the elevation broker. Reconcile an interrupted removal as complete only when the source is safely absent; cancel it when still present. A retry never performs unconditional deletion. Ordinary desktop files still enter Recovery through the delayed, stable parking path.
- Schema v8 preserves v7 decisions, checkpoints, and fingerprints. Existing pending shortcuts receive one comparison with parked identities; matching items start the full configured delay. Approved shortcuts retain their decision. Persist the evaluated flag so changes or failures that return a scheduled shortcut to review do not restart automatic parking on every scan.
- When the elevated helper handles a Recycle Bin delete, compare its effective SID with the interactive shell user's SID. If they differ, fail closed rather than moving a Public Desktop shortcut into another administrator's Recycle Bin.
- Desktop Recycle Bin deletion uses a single-file Shell operation with `FOF_ALLOWUNDO` and no confirmation, error, or progress UI. Map Shell's legacy `DE_ACCESSDENIEDSRC` result to Win32 `ERROR_ACCESS_DENIED` so only the bounded DG helper can request elevation. Keep the signed-in-user versus helper SID check in that helper.
- Reject reparse points on candidate files, staging directories, per-shortcut recovery folders, the Recovery root, and DG's data directory. Revalidate both Desktop roots before management; if either path changed, keep prior decisions and block operations on the changed location.
- Path-based checks in the one-operation elevated helper do not protect against a malicious process running under the interactive user's own SID that swaps that user's Desktop or Recovery directories during an operation. Same-user adversaries remain outside the current security goal; protecting against them would require handle-relative directory traversal and file operations with dedicated race-injection coverage.
- Enable shortcut management only after a complete scan of the current user Desktop. An incomplete scan keeps existing decisions visible but disables file operations until a complete scan succeeds.
- Keep the state file bounded to 4 MiB and write it to a temporary file before replacing the prior state. Reject oversized or malformed data without replacing the existing state. Schema v7 adds an auto-parking delay and optional 32-byte shortcut-identity fingerprints; migrate older states with a 5-minute default without changing existing decisions or checkpoints. Backfill fingerprints idempotently from validated Recovery files, preserve files on any read/parse failure, and do not infer identity from a filename. Bound a full backfill to 64 MiB per startup.
- Bound both startup backfill and scan identity reads to 64 MiB each. Reserve the applicable per-file limit plus one byte for the final EOF check before each attempt. Charge completed reads even if parsing fails; retain the full reservation when the amount read cannot be determined.
- Keep notification activation data to a validated opaque shortcut ID resolved against current local state. Never put raw paths into activation arguments. Sanitize and bound names shown in notification text, and show at most five notifications per scan.
- Treat keyboard shortcuts as user input and route them through the same current-selection, state, and file-operation checks as the corresponding UI commands. **F2** and **Delete** act only on the selected shortcut while the list has focus and the action is enabled; Recovery deletion still requires confirmation, and key input never supplies a path or command.
- Register only the DG-owned value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`. The command targets the current DG executable and includes the fixed `--background` argument only when the validated `StartMinimized` state setting is enabled; DG does not accept arbitrary commands from state or notification data.
- Package only the self-contained executable, static offline HTML and Markdown README files, the DG icon used by the HTML guide, and the license in the portable ZIP. Generate the HTML from `README.portable.md` using a restricted Markdown renderer that escapes source text, emits no scripts or external resources, and permits only local package links. Recommend a stable folder under the signed-in user's profile with its normal per-user ACLs, not a shared writable folder, because the same executable path is used for the one-operation UAC helper. Quote the absolute executable path in the Run value. On every launch from a relocated folder, refresh that value from the actual running executable; never trust a path loaded from saved state.
- Read only the current user's `AppsUseLightTheme` personalization value for UI colors. Treat it as untrusted presentation input, fall back to the light palette if it is unavailable, and let Windows high-contrast colors take precedence. It must not affect shortcut policy, persistence, or file operations.
- Keep event records local and limited to file name, path, and timestamp for at most 90 days. Bound notification text and preserve recovery data separately from the event log.
- Migrate schema v1 by preserving its Public checkpoint: paths in that checkpoint are the existing approved baseline; Public shortcut paths absent from it become pending when first scanned after migration. Migrate schema v2 and v3 without changing existing decisions or checkpoints. Initialize `StartMinimized` to true when migrating any schema v1-v3 state. Migrate schemas v4-v8 to the current schema without changing decisions, checkpoints, or shortcut names; fields introduced in schemas v7-v8 default safely. Schema v9 uses the existing optional target-name field for restore and desktop-move intents; v8 pending operations with no target name continue using their original basename. Mark only a validated in-progress `Creating` record as DG-created because that operation is exclusive to DG's explicit creation flow; never infer ownership of a completed shortcut from its name. The schema v3 creation-operation hash is accepted only for a validated in-progress User Desktop shortcut creation. If state is corrupt, preserve it and require a safe recovery path; never silently reset approvals or reinterpret either Desktop as a new baseline. Do not trim recovery records to meet a storage cap; fail closed and preserve the prior state.

## Dependencies and release checks

- Keep exact dependency versions and commit NuGet lock files. NuGet vulnerability auditing covers direct and transitive dependencies.
- The Windows App SDK is required for unpackaged Windows notifications. Ship its self-contained x64 runtime with the application; do not introduce network access or runtime downloads.
- Publish the app as a self-contained compressed single-file executable in a portable ZIP with the offline HTML and Markdown README files, DG icon, and license. The configured self-extraction places bundled files under the current user's `%TEMP%\.net` directory before startup. Keep the default per-user extraction location; never redirect it to a shared writable directory. Recommend running from a stable, per-user protected folder. Keep the main process unelevated and validate extraction, same-user UAC, over-the-shoulder UAC, a folder path containing spaces, and startup-path refresh after relocation on Windows 11 before release.
- Review security-related .NET analyzer diagnostics. Do not suppress one without recording why and what compensating control is used.
- Before a release, restore with `--locked-mode`, run `dotnet package list --vulnerable --include-transitive`, and review every finding. Unresolved high or critical advisories block release unless a documented mitigation makes the affected code unreachable.
- The GitHub Actions release workflow accepts only version tags, builds the package on a disposable Windows-hosted runner with read-only repository access, and transfers only the ZIP through a one-day artifact. Pin official actions to verified full commit SHAs. Keep `contents: write` confined to the separate draft-release job, scope `GH_TOKEN` to its release step, and do not check out or execute tagged project code in that job. Restrict version-tag creation to release maintainers. The workflow creates a draft only when no release exists for that tag; it never replaces an existing release or asset. Review the tagged source and complete all release checks before publishing the draft.
- Automated security regression tests reject invalid and unknown notification activation IDs and verify that coalesced scan-request floods and simulated watcher errors trigger a full rescan. Actual Windows watcher overflow behavior remains a manual release check.
- Automated file-operation tests must use temporary directories. Manually validate tray lifecycle, sign-in registration, Windows notification display and activation, watcher-error recovery, same-user and over-the-shoulder UAC, UAC cancellation/policy denial, ACL inheritance, rename and Delete keyboard actions against the selected shortcut, Properties for `.lnk` and `.url`, Hidden preservation and clearing, Recycle Bin behavior, confirmed permanent Recovery deletion, lock handling, and failure handling on Windows 11 before release.
